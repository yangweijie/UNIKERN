# Phase 30 证据 — reduce 首次归因：串行 pass-2 才是主项；√n 律在第四个点被自己的数据否证

本机：Windows 11 + AMD **RX 6600M（gfx1032）**，ROCm 7.1。日期 2026-10-28。
判据先写死在 `task_plan.md` 的"Phase 30 预登记"。**本轮不改生成器**（理由见最后一节）。

## 现状（读码，非猜测）

发射的 reduce 程序跑两个内核：`uk_reduce_part`（`nP` 条线程各做 `n/nP` 个元素的跨步折叠）与
`uk_reduce_sum`（**一条线程**串行折叠那 `nP` 个部分和），而 `nP = UK_REDUCE_WIDTH = min(L, 4096)` 向上取到 256 的倍数，**在生成期定死**（当时 codegen_hip 的 724 行），
运行期不看任何设备自报量。两个分量随 `nP` **反向**变化，所以"加大宽度"必须先归因才谈得上。
**时点演进（2026-10-29 注）**：D9/Phase 44 之后这条已不成立——宽度改由设备自报量在运行时推导，
发射点是 `uk_reduce_width_plan`（`src/codegen_hip.cpp:874`）；上面 724 是 Phase 30 当时的位置，按
"转录不改写"保留为文本。

## 仪器

`probe/uk_reduce_width_probe.cpp`：折叠次序与发射内核逐字一致（升序跨步 + 串行折叠），
分别计时 `part-only / sum-only / both`；数据取全域 2⁻⁶ ⇒ **期望值可以先算**（n/64），
探针自己打印 `rel`，六个 n 全部 `rel=0.000e+00`（仪器自校通过，才有资格读时间）。
`n ∈ {2²⁰, 2²², 2²⁴, 2²⁶}`、`nP ∈ {1024 … 32768}`。

## √n 律：在两个新点上被自己的数据否证

由 `T ≈ a·n/nP + b·nP` 极小化得 `nP* ∝ √n`；把常数锚在**现役** 4096（它在 n=2²⁰ 实测最优）：
预测最优 nP = 4096 / 8192 / 16384 / 32768。实测最优 = **4096(2048 同阶) / 4096 / 16384 / 16384**：

| n | 预测 nP\* | 实测最优 nP | 判定 |
|---|---|---|---|
| 2²⁰ | 4096 | 2048–4096（0.1572 vs 0.1582，差 0.6%） | 一步之内 |
| 2²² | 8192 | 4096（0.3046 vs 0.3078，差 1.05%） | 一步之内 |
| 2²⁴ | 16384 | **16384** | 命中 |
| 2²⁶ | 32768 | **16384**（1.8723；32768 是 2.5777，**差 38%**） | **否证** |

原因写在数据里：**pass-1 的带宽会饱和**——大 n 时 `part_GBps` 在 16384 处 188.1，到 32768 反而**降到** 166.6；
而 pass-2 的串行折叠严格线性增长。于是最优点被"饱和点"卡住，不再随 √n 走。
⇒ **本轮不采纳任何写进生成器的公式**：能把数据说对的规则形如
`nP = clamp(4096·√(n/2²⁰), 4096, 16384)`，其中上限 **16384 是这只卡的实测饱和常数**，
而本项目全天坚持的口径是"选档量必须来自设备自报，不许抄标称/拟合常量"
（Phase 20/21 为此拒绝过 `14` 这个标称 CU 数）。试图用设备自报量表达它也不成立：
按 occupancy 推导（`maxThreadsPerMultiProcessor=2048 × cu=14 = 28672`，或 4 块/CU=14336）
这两个值在 step 3 里都补测了：**28672 明显更差**（n=2²⁶ 时 2.0374 ms 对 16384 的 1.8743，慢 8.7%），
14336 与 16384 打平但**破坏出厂对拍的精确性**（见下节）⇒ 设备自报量给不出既快又保住 `max_rel=0` 的上限。

## 交给用户的两个决定（我不替用户定）

- **D9（新）**：是否接受一条**由本机扫测拟合**的宽度规则
  `nP = clamp(4096·√(n/2²⁰), 4096, 16384)`？收益实测：**n=2²⁴ 1.67×、n=2²⁶ 2.49×**，
  而 n ≤ 2²² 不退步（最好情况差 ≤1.05%）。代价：破坏"宽度只来自设备自报量"的口径，
  并把一个卡相关常数写进生成器（换一只卡需要重新扫测）。
- **结构修法需要 D8 同类决定**：把 pass-2 并行化（块内归约）能从根上消掉这个取舍——
  但它**改变最终和的折叠次序**（AGENTS 第 3 条：改算术顺序=改结论），
  会使全部已入库的 reduce `max_rel` 读数换含义，且与 D8（差分参考口径）纠缠。**不擅动。**
- 附：宽度变化本身只改分组，不改折叠次序；对精确可表示的出厂数据 `max_rel` 恒 0，
  对非精确数据 Phase 19 实测"nP 越大越接近精确和、但与 fp32 顺序 CPU 参考的分歧越大"——
  这也是 D9 值得等的理由之一。

## step 3 的反转结论：**启动参数被差分检查本身约束**（`device-cap.txt`）

为了搞清"上限能不能写成设备自报量"（这样就不必抄拟合常数），测了 `14336 = 4 块/CU×256×cu`
与 `28672 = maxThreadsPerMultiProcessor×cu`：

| n | nP | part | sum | both | result | **rel vs 精确值** |
|---|---|---|---|---|---|---|
| 2²⁴ | 14336 | 0.3784 | 0.3615 | **0.7262** | 262144.0 | 0.000e+00 |
| 2²⁴ | 16384 | 0.3364 | 0.4220 | 0.7361 | 262144.0 | 0.000e+00 |
| 2²⁴ | 28672 | 0.3138 | 0.7080 | 1.0169 | 262144.0 | 0.000e+00 |
| 2²⁶ | 14336 | 1.5471 | 0.3664 | 1.9631 | **1048408.0** | **−1.602e−04** |
| 2²⁶ | 16384 | 1.4317 | 0.4168 | **1.8743** | 1048576.0 | 0.000e+00 |
| 2²⁶ | 28672 | 1.2665 | 0.7218 | 2.0374 | **1048432.0** | **−1.373e−04** |

两件事同时成立：

1. **时间上**：14336 与 16384 基本打平（2²⁴ 上 14336 好 1.4%、2²⁶ 上差 4.7%），
   而设备满载的 28672 明显更差（1.0169 / 2.0374）⇒ **"填满设备"不是正确的上限**，
   所以 occupancy 推不出那个 cap（step 2 里我把它写成推测，这里给成实测：28672 在 2²⁶ 比 16384 慢 8.7%）。
2. **精度上（本轮最有用的一条）**：n=2²⁶ 时**只有非 2 的幂的 nP 出现偏差**
   （14336、28672 → `rel≈−1.4e−4~−1.6e−4`），而 step 2 里全部 2 的幂档（1024…32768）都是 `rel=0`。
   机制是算术：全域 2⁻⁶ 时每个部分和是 `k/64`，`k` 非 2 的幂 ⇒ 折叠到 2²⁰ 量级时尾数超出 fp32 的 24 bit ⇒ 舍入；
   `n/nP` 为 2 的幂时各步都是 2 的幂相加 ⇒ 精确。
   ⇒ **出厂对拍数据的"任意次序都精确"这个性质，会随启动宽度失效**：
   `max_rel` 不再是 0（虽仍在 2⁻⁵ 容差内，账本会照收），
   而本项目全部已入库证据的口径恰恰建立在 `max_rel=0` 上。**这条约束此前没被写进任何文档**，
   是本轮测出来的（7 个 2 的幂档 rel=0 + 2 个非幂档 rel≠0）。

### 由此收紧 D9 的表述

候选集必须同时满足：① 是 2 的幂（保住出厂对拍的精确性）；② 在时间上不劣于现役 4096。
在 2 的幂里，实测最优是 **n ≤ 2²² → 4096、n ≥ 2²⁴ → 16384**；
形如 `nP = clamp(2^round(log2(4096·√(n/2²⁰))), 4096, 16384)` 的规则能复现全部四个点
（2²⁰ 差 0.6%、2²² 差 1.05%、2²⁴/2²⁶ 命中），但**上限 16384 仍是本机拟合常数**，
且 occupancy 方向已实测推不出它（见上）。⇒ 是否采纳交给用户（D9），本轮不动生成器。
