# Phase 46 — D8 取证：规格要求的**两档** CPU 参考，我们只用了一档

主机：Windows 11，MinGW-w64 GCC 13.2（纯 CPU）。**没有动生成器、没有动容差、没有动任何判据**，
因为 D8 是"等用户定口径"的开放项（AGENTS.md 待决事项）；本相交付的是**让那个决定可以被做的数字**。

## 规格到底说了什么

`requirements.md:10`：「正确性验证以 **CPU 参考实现**为基准（**标量 + 分块两档**）」；
`requirements.md:34` 与 `design.md:132` 重复同一句。也就是说"分块档"不是候选方案，是规格要求的一半。
出厂实现只有标量档（`cpu_reduce` `src/reference.cpp:24` 的 `cpu_reduce` = `float acc=0.f; for i: acc+=x[i];`）。

## 三条实测结论

1. **对已入库证据是中性的**。在今天生成程序 verify 段真正使用的输入上（常量 `fill=2^-6`，
   n=2²⁰ 与 n=2²⁴ 两档，宽度 16384 与 4096 都试），两档 fp32 求和**逐位相同**，
   且都**恰好等于闭式精确值**（16384 / 262144，`rel_vs_exact = 0`）。
   ⇒ 将 reduce 的参考换成"分块档"，**不会改变任何一条已入库 `max_rel=0` 读数的含义**——
   这正是 D8 当时卡住的那个理由，现在被数据关掉了（只对 reduce 成立，见"未覆盖"）。
2. **D8 的病理在 CPU 上被复现，且方向是参考的错**。Phase 19 记录的输入形状（交替 `1e6 / 1e-6`）：

   | n | 宽度 | 标量档 vs 精确 | 分块档 vs 精确 | 两者逐位相同？ |
   | --- | --- | --- | --- | --- |
   | 2²⁰ | 16384 | `+7.238812e-03` | `−5.556250e-05` | no |
   | 2²⁴ | 16384 | `+4.154000e-02` | `−5.556250e-05` | no |
   | 2²⁴ | 1024 | `+4.154000e-02` | `+1.856875e-04` | no |

   标量档在 n=2²⁴ 上**越过 2⁻⁵=3.125e-02**，而分块档离精确值小三个数量级以上 ⇒ 被判 FAIL 的一方
   是更准的一方，正如 Phase 19 所记。参考档位的选择本身就能消掉这条，**不需要改容差**。
3. **"宽动态范围"不等于"参考更差"**——方向取决于输入的符号与幅值结构。另一类宽输入
   （`2^linspace(−40,40)`，确定性 LCG 定符号）里**标量档反而更准**（`+6.65e-08` vs `−4.36e-07`）。
   所以"哪一档是真值"不是一个可以由输入类别口头断言的属性；单一档参考是错的仪器，
   不是碰巧这次才错。

## 与 Phase 19 真机读数的对账（第二台仪器）

| 量 | Phase 19 真机/臂 | 本相 CPU | 是否一致 |
| --- | --- | --- | --- |
| `seq_err` @ n=2²⁰ | `7.23881e-03` | `+7.238812e-03` | **逐位一致** |
| 两轮归约误差 @ n=2²⁴, nP=1024 | `1.86e-04` | `+1.856875e-04` | 一致（4 位有效） |
| 两轮归约误差 @ n=2²⁴, nP=16384 | `5.56e-05` | `−5.556250e-05` | 一致（符号本相才知道） |
| 参考 vs 精确 @ n=2²⁴ | `3.988e-02` | `+4.154000e-02` | **不一致（差 4%）** |

最后一行的分歧没有被抹平：Phase 19 的 `3.988e-02` 与我的 `4.154e-02` 是同一量级的同一结论，
但数值不同；最可能的原因是当时的"精确和"与本轮闭式（`(n/2)·(1e6+1e-6)`，且
`fp32(1e6)+fp32(1e-6) == 1e6f` 说明**闭式不能写在被判的精度里**）取法不同，
以及交替序列的起点/奇偶约定。本相没有 Phase 19 的探针源码里那一行的精确定义可比，
所以这条只能记作**未对齐的第二仪器**，不能记作复现成功。

## 复现

```bash
c++ -O2 -std=c++20 -o build/uk_ref_tiers.exe probe/phase46_reference_tiers.cpp
./build/uk_ref_tiers.exe shipped   # 结论 1：两档逐位相同且等于闭式精确值
./build/uk_ref_tiers.exe alt       # 结论 2：D8 的输入形状，标量档越门
./build/uk_ref_tiers.exe frozen    # 规则 7 的冻结边界：n=2^25 时两档开始分岔
./build/uk_ref_tiers.exe wide20 && ./build/uk_ref_tiers.exe wide24   # 结论 3：方向会反过来
```

完整转录在 `tiers.txt`（仪器第一行自己打印 `sizeof(long double)=16 digits=64`，
即 Kahan 列只有 64 位尾数，**不是**精确参考；有闭式的行才用闭式）。

## 未覆盖（不冒充做过）

- **只对 reduce**。gemm/conv 的 verify 输入是零均值锯齿（`initA mod 17` / `initB mod 13`），
  一个周期内的乘积和恰为 0 ⇒ `max_rel=0` 是结构性的，本相没有重新测量它们的两档差异。
- **没有实现任何换档**。`cpu_reduce` 与生成程序的 verify 段一字未动；换档会动发射产物字节，
  并把"参考"这一列变成实现选择——那是 D8 的决定，不是本相的决定。
- 若采纳分块档，需要同时决定：三后端是否都用同一档（Metal/OpenCL 的 runner 有自己的 `cpu_reduce`
  副本）、`max_rel` 的口径列要不要进结果行、以及 `[R6.4-order]`/`[R6.6-model]` 两条臂的重写。
- Phase 44 遗留的两台仪器对 4096 基线 `kernel_ms` 的分歧，本相未查。

## 给用户的决定项（D8，现在有数了）

A. **换参考为分块档**（规格本来就要求两档，实测对已入库 reduce 证据中性）；
B. **保留标量档但把容差与 n 绑定**（会让所有旧 `max_rel` 口径改含义——本相没有找到这个理由）；
C. **维持现状**（明知在宽动态范围输入上，被判 FAIL 的是更准的一方）。
本相按"不替用户决定"的约束停在取证。
