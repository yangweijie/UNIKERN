## 盲区是从读码确定的（不是猜测）

发射出来的 reduce 程序里，差分验证段与计时段用的规模不同——生成侧的两处证据（行号取自本机，
`probe/anchors_check.py` 的门会跟着核）：

```
src/codegen_hip.cpp:781   // Differential verify: 2^20 values of 2^-6 sum to 16384 in ANY fp32
src/codegen_hip.cpp:724   int width = L < 4096 ? L : 4096;
src/codegen_hip.cpp:808   const int UK_REDUCE_WIDTH = " << width << ";
```

差分验证段跑的是**固定 2²⁰ 实例**，而 `UK_REDUCE_WIDTH` 来自**声明的 L**。也就是说
`UNIKERN_RESULT` 里那个 `max_rel` 永远描述的是那个小实例——Phase 30 发现的
"宽度会让折叠失去精确性"这类事，**门禁在结构上就看不见**。
（scratch 副本在 `uk_run/p31/uk_amd.cpp`，它会被清掉，所以本相的引用一律指向生成器行号。）

## 网格实测（`fold-exactness-grid.txt`，18 格，仪器先报 `result/rel` 再报时间）

`n` 取计时规模的值（不是验证实例的 2²⁰），宽度取现役 4096 与两种非幂宽度：

| n | 期望和 | nP=3072 | nP=4096（现役） | nP=14336 |
|---|---|---|---|---|
| 2²⁴ | 262144.0 | 0 | 0 | 0 |
| 2²⁴+1 | 262144.0 | **−5.960e−08** | **−5.960e−08** | **−5.960e−08** |
| 2×10⁷ | 312500.0 | 0 | 0 | **+1.154e−04** |
| 2²⁵ | 524288.0 | **+1.526e−05** | 0 | **−3.052e−05** |
| 2²⁶ | 1048576.0 | **−3.052e−05** | 0 | **−1.602e−04** |
| 2²⁶+4096 | 1048640.0 | **+4.959e−05** | **−4.577e−05** | **−1.221e−04** |

预登记四条预期的对账：

1. **成立**：整除且 chunk 为 2 的幂 ⇒ `rel=0`（现役 4096 在 2²⁴/2²⁵/2²⁶ 三档全 0）。
2. **成立且量级命中**：非 2 的幂 chunk ⇒ `rel≠0`，实测 **5.96e−08 … 4.96e−05**，落在我写死的
   1e−7~1e−4 区间内。**但触发条件比我原先想的更准**：`n=2²⁶+4096` 是**整除**的
   （67112960 / 4096 = 16385），出错是因为 **chunk 16385 不是 2 的幂**——
   所以正确的判据是"chunk 是否 2 的幂"，不是"n 是否被 nP 整除"。这条修正是本轮的实测产出。
3. **成立**：非 2 的幂宽度在大 n 上出错（14336 在 2×10⁷/2²⁵/2²⁶ 分别 1.154e−04 / −3.052e−05 / −1.602e−04），
   但**不普遍**：2²⁴ 上 3072 与 14336 都还是 0 ⇒ 单看宽度不足以保证精确，还得看 chunk 的比特形状。
4. **成立（这是结论的核心）**：所有非零 `rel` 与门限 2⁻⁵=3.125e−02 差 **≥195 倍**
   ⇒ 没有任何出厂门禁能因这类误差报错；`verify=PASS max_rel=0` 里的"0"是**验证实例的性质**。

## 机制不需要真机：CPU 侧逐位复现

`python` 里按同样次序折叠 fp32：

| 折叠 | CPU rel | 真机 rel | 对应格 |
|---|---|---|---|
| 4096 × 256.015625 | **4.57736e−05** | **−4.577e−05** | 2²⁶+4096 / nP=4096 |
| 14336 × 73.140625 | **1.60222e−04** | **−1.602e−04** | 2²⁶ / nP=14336 |
| 4096 × 256.0 | 0 | 0 | 2²⁶ / nP=4096 |

同值到最后一位 ⇒ 这是 fp32 累加的算术事实（总值到 2²⁰ 量级时量子是 2⁻⁵，
而数据步长是 2⁻⁶，非 2 的幂的加数会在某一步丢掉那个低位），不是驱动/硬件的怪异行为。

## 进测试套件：`[R6.5-blind]`（`tests/acceptance.cpp:1634/1639/1647`；Phase 31 当时是 :1454/1459/1467）

把上面三件事写成确定性 CPU 臂（与 `[R6.4-order]` 同一手法，不需要真机）：
① 2 的幂 chunk 必须逐位精确；② 非 2 的幂 chunk 必须**不**精确且 `rel<1e−4`；
③ 两者都必须在门限的 **1/100 以下**（即"盲区是结构性的，不是可以调阈值调出来的"）。
