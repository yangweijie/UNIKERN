# Phase 34 证据 — 折叠误差的模型（41 格全中）+ 收回我上一相写过宽的 G10 说法

本机：Windows 11 + AMD **RX 6600M（gfx1032）**，ROCm 7.1。日期 2026-10-28。
预登记在 `task_plan.md` 的"Phase 34 预登记"。

## ① 模型：两趟折叠的 fp32 误差可以**算**出来，不用猜

出厂 reduce 的数据是常量填充（计时段 `0.5f`，验证段 `2⁻⁶`）。对 `n` 个元素、`nP` 条线程：

- 线程 `t` 折叠的下标是 `t, t+nP, …` ⇒ 个数 `k_t = floor((n-1-t)/nP) + 1`（`t ≥ n` 时为 0）；
- 部分和 `= k_t · fill`，当 `k_t < 2²⁴` 时**这一步是精确的**（整数乘 2 的幂）；
- ⇒ **其余全部误差来自 pass-2 那条串行 fp32 累加**，可以在 CPU 上按同一次序逐格算出来。

**对账结果：41 格真机读数（Phase 28/30/31/33 全部记录过的 `rel`）逐格比对，mismatch = 0** ——
零/非零一致、量级一致（比对容差 5%，对应转录里 4 位有效数字的打印精度）。
附带结论：真机 pass-2 与"串行、不重结合"一致（若编译器重排过累加，模型不可能逐格对上）。

## ② 臂：`[R6.6-model]`（纯 CPU，`tests/acceptance.cpp`，19 格入表 + 两条结构性断言）

断言三件：①模型对 19 格读数逐格复现（含三个反直觉点：`5×10⁷` 四档全偏、`3×10⁷` 只有 16384 偏、
`2×10⁷` 只有 2048/8192 偏）；②验证实例 `n=2²⁰` 在**所有可能选到的宽度**上都精确；
③模型给出的最坏偏离 `2.40667e−04` 仍低于验收容差 `3.125e−02` 的两个数量级以上。

**摘除控制三条全红**（`arm-removal.txt`，`probe/phase34_model_arm_probe.py` rc=0，
均落在 `[R6.2/R6.4]` `tests/acceptance.cpp:1576`）：

| 腿 | 改动 | 为什么该红 |
|---|---|---|
| 1 | pass-2 改成 double 累加 | 模型预测全为 0 → 与"某些格本来不精确"矛盾 |
| 2 | 填充值换成非 2 的幂（`0.1f`） | 部分和不再是精确缩放 → 预测偏离实测 |
| 3 | 把一条实测读数改成 0 | 表格不是装饰：模型必须与它比对的读数一致 |

**这一相最有教育意义的一条**：腿 2 的第一版我用的是 `0.5f`，**结果是绿的**。原因不是运气而是数学：
按 2 的幂整体缩放不改变 fp32 的**相对**舍入 ⇒ 那条控制什么也没测。
换成非 2 的幂的 `0.1f` 才真正会红。**"能跑出的控制"与"能失败的控制"是两件事**——这条已经写进 `AGENTS.md` 的探针纪律。

## ③ 收回一处写过的话（G10 的严重性）

上一相我把 G10 写成"**已出货的宽度在某些规模上就不精确，而验证看不见**"，并说"账本会安静收下带误差的结果"。
读码核对：计时段的 `Y` 拷回主机后**没有任何代码使用它**（发射点是 `hipMemcpyAsync`（`src/codegen_hip.cpp:946`）那句 `"d2h tY"`；原文写的 844 是当时的位置），
`max_rel` 只来自 2²⁰ 验证段，账本记的是 ε 与时间，不是这个和值
⇒ 那是**覆盖缺口**（该规模的结果压根不在验证范围内），**不是"已入库证据被污染"**。
已在 6 处就地改口（`AGENTS.md` 第 7 条、`findings.md` Phase 33 段、`task_plan.md` Phase 33 行、
`docs/acceptance-mvp.md` v26 标题与正文、`docs/evidence/phase33/README.md`、`progress.md` 续18），
并在 v27 记录这次自我修正。模型与臂不受影响——它们本来只声称"算得出误差"，没声称"证据被污染"。
