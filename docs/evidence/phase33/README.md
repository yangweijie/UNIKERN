# Phase 33 证据 — 2 的幂宽度也不保证精确：现役 4096 在真实规模上已经会偏

本机：Windows 11 + AMD **RX 6600M（gfx1032）**，ROCm 7.1。日期 2026-10-28。
预登记的三分支判读在 `task_plan.md` 的"Phase 33 预登记"；原始读数 `pow2-widths.txt`（32 格）。

## 问的问题

Phase 30/31 得出的可用说法是"2 的幂宽度 ⇒ 折叠精确"。**它只在被测过的 n 上成立**，
而机制（运行和超过 `2²⁴·2⁻⁶ = 262144` 后 ulp 粗于 2⁻⁶）说明精确性主要由 `n` 决定。
所以本轮只测 2 的幂宽度，问一句：**现役 4096 的 `rel=0` 是保证，还是样本选择的偶然？**

## 落在预登记的分支 2（不是分支 1）

- **没有任何宽度全格精确**：n=5×10⁷ 时**四档全部** `rel≠0`，包括现役 4096（`+5.44e−05`）。
  ⇒ **现役出货路径在真实规模上已经会产生带误差的 reduce 结果**，而差分验证（固定 2²⁰）看不见它。
  这不是"换宽度会破坏精确性"，而是"精确性本来就不由宽度保证"——**我此前把这句话写宽了**，
  四处记录已按本轮数据改口径（见"修正了哪些说法"）。
- **精确性由 `n` 的量级主导，宽度只决定余下的运气**：越过 `n = 262144·64 = 1.678×10⁷` 之后，
  同样"2 的幂"的宽度里出现了 0 与 2.4e−04 并存（3×10⁷：2048/4096/8192 精确、16384 偏 +2.41e−04；
  2×10⁷ 反过来是 2048/8192 偏、4096/16384 精确）。⇒ 想说清边界需要的是 `(n, nP)` 二维网格，
  **本轮不再外推成规则**（不给两点/四点编法则）。
- **速度侧结论很干净**：`nP=16384` 在**八个个 n 上全部是最快档**，对现役 4096 的比是
  **1.65× / 1.65× / 1.80× / 2.04× / 2.06× / 2.31× / 2.49× / 2.50×**（单调随 n 增大）。
  且 16384 可由设备自报量导出：`per_cu × cu × blockDim = 8 × 14 × 256 = 28672` →
  向下取 2 的幂 = **16384**，与实测最优同值（这条推导是本轮新写的，之前只是当猜想）。
