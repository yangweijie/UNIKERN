# Phase 28 证据 — C × OCB 曲线：增益符号**不**随 C 单调，因此不采纳"按 C 选档"的规则

本机：Windows 11 + AMD **RX 6600M（gfx1032）**，ROCm 7.1。日期 2026-10-28。
判据先写死在 `task_plan.md` 的"Phase 28 预登记"；脚本 `probe/phase28_ocb_c_sweep.py`（打补丁→发射→还原→计时）。

## 为什么要有这一相

Phase 27 只有两个点：ocb=16 在 C=32 慢 9.7%、在 C=16 快 7.5%。两点可以编出一条"按 C 分档"的规则，
也可以被第三点推翻——所以先测成曲线，再决定选档器动不动。

## 两条曲线的实测（`sweep-tile16` = `sweep.txt`，`sweep-tile8.txt`；全部 `verify=PASS max_rel=0.000000e+00`）

**tile 钉死，Oc=64、空间 256² 固定，只变 C；ocb ∈ {8,16} 各 3 跑，取中位数**

| C | tile=16：ocb8 → ocb16 | 16 相对 8 | tile=8：ocb8 → ocb16 | 16 相对 8 |
|---|---|---|---|---|
| 8 | 0.906 → 0.725 ms | **+24.9%** | 0.955 → 0.774 ms | **+23.4%** |
| 16 | 2.073 → 1.728 ms | **+20.0%** | 2.745 → 2.251 ms | **+22.0%** |
| 32 | 7.020 → 7.802 ms | **−10.0%** | 9.470 → 10.405 ms | **−9.0%** |
| 64 | 不可测（82944 B > 65536，见 Phase 29） | — | 41.425 → 37.169 ms | **+11.5%** |

每格 3 跑的极差：tile=16 组 ≤1.03%，tile=8 组 ≤2.21%（都低于预登记的 3% 门槛）；
tile=8 那条曲线 12 格全部到位，**离散度门槛 PASS**。

## 判定：**预登记的第 2 条（符号沿 C 单调）不成立**

tile=8 曲线上符号是 `+ + − +`：C=32 是唯一的负号，**C=64 又翻回正**。
⇒ **不存在一个可以用 C 表达的翻转点**，"最优 OCB 是 C 的函数"这个 Phase 27 的猜想被自己的数据否证；
更准确的说法只能是：**最优 OCB 取决于 (C, Oc, tile, 网格大小) 的联合作用，其机制在本机未定**。
按预登记的第三条出口执行：**候选集保持 `{8,4,2,1}`，生成器不因这条曲线改动**。

预登记的三条门槛逐条对账：

| 条 | 门槛 | 实测 | 判定 |
|---|---|---|---|
| 1 | 每 C 的 3 跑极差 < 3% | 全部 ≤2.21% | **通过**（tile=16 的 C=64 一格不存在，原因见 Phase 29，不是离散度问题） |
| 2 | 16 相对 8 的符号沿 C 单调，且翻转由 ≥2 个相邻 C 支持 | tile=8：`+ + − +`，非单调 | **不通过** ⇒ 不采纳 |
| 3 | 全部运行 `max_rel=0` | 42 次有结果的运行全 `0.000000e+00` | **通过** |

## 两处如实的自我修正

1. 脚本第一版把"格数不足"和"极差超标"合并成同一个 `spread gate = FAIL` 标签——`sweep.txt` 末尾那行
   FAIL 是 **C=64 缺格**造成的，不是极差超差（极差实测 ≤1.03%）。第二版分开报告，`sweep-tile8.txt` 尾行
   是 PASS。**教训：仪器的失败标签必须区分"数据差"与"数据缺"，否则下一个读者会把缺格读成噪声。**
2. 计时上下文改成了**直接运行生成的可执行文件**（24 次同一上下文），因为要在 4 个 C 上跑同一套；
   这与 runner 上下文相差约 1.9%（Phase 26 记过），所以**本表读数不与历史带互比，只在轮内比**。
